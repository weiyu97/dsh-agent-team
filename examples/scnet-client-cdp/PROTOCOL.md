# SCNet 客户端桥 · 方案与操作流程（v0.3 草案，待审）

> 2026-11-11 02:30 · 澪。本文只描述“应该怎样”，不宣布已实现。

## 1. 目标

任何会话里派给 SCNet 的任务，都能：
1. 在 SCNet 客户端里**开一个独立新会话**执行（上下文不串）；
2. 有明确的“开始/结束”判定，不会把中间态当完成；
3. 产出落 `outbox/` 并回共享信箱；
4. 失败可重试、可退回队列、可人工接管。

## 2. 角色

| 角色 | 是谁 | 职责 |
|---|---|---|
| 派活方 | 任意 dsh 会话里的澪 | 调 `scnet-dispatch.sh` 投队列 |
| 队列 | scnet-mcp 18889 | 只存状态，不执行 |
| 桥 | `scnet-client-bridge`（systemd） | claim → 新会话 → 发送 → 等完成 → 回写 |
| 执行体 | SCNet-Max 客户端（ITX） | 真干活，产出文本/文件 |

## 3. 任务状态机（以队列为准）

```
queued --claim--> doing --send--> running --finish--> done
                                  │
                                  ├--超时/失败--> retry(≤2) --仍失败--> blocked
                                  └--ask 超时--> queued（重排）
```

规则：
- claim 必须原子：`update(doing, progress="claimed by <bridge>")`，并写 `claimed_at`。
- 重启桥时先扫 `doing` 且 `claimed_at` 超 10 分钟的 → 回 queued（孤儿回收）。
- `done` 只在**确认生成真的结束**后写；result 为空或只有“正在思考”不许标 done。

## 4. 会话生命周期（核心）

一次派遣 = 一个会话：

1. 点「新建任务」（`button.sidebar-nav-button`）→ 若有项目菜单，选 `linux_dfy` 或第一项。
2. 等新会话就绪：`.chat-message--response` 数 = 0 且 toolbar 标题变化（最多等 8s）。
3. 聚焦 `.ProseMirror` → 清空 → `Input.insertText` → 点 `button[aria-label="发送消息"]`。
4. 等完成（见 §5）。
5. 读最后一条 `.chat-message--response .chat-block-markdown` → 写 `outbox/<task_id>.reply.md` → 推板 `产出/`。
6. 把会话标题（它自动取任务首行）记进回执，便于人查。

**并发**：见 §13 实测结论——切会话不中断后台生成，可「批量发射 + 顺序收集」。默认并发度 2~3，别无限开。

## 5. 完成判定（这轮翻车的地方）

**不能**用“文本长度稳定 2~3 次”判完成——流式输出中间会停（“正在思考…”“正在处理 14 秒…”）。

判定改为组合条件，全部满足才算完：
- 「停止生成」按钮消失（`button` 文本/aria 不含 停止生成）；
- 页面不再含 `正在思考|生成中|正在处理`；
- 最后一条 response 文本在 **8 秒内无变化**；
- 最后一条 response 非空。

任何一条不满足 → 继续等，直到总超时。

## 6. 超时与重试

- 单任务总超时：10 分钟（可配 `SCNET_TASK_TIMEOUT`）。
- ask 内部等待 300s，超时返回“不完整”标记，桥区分 `ok / timeout / error`。
- timeout → 任务回 queued，attempts+1；attempts ≥ 3 → blocked + 落一条板子消息。
- error → 同 timeout 处理。

## 7. 产出收集

SCNet-Max 有两种产出：
1. **聊天文本**（脚本/文档内容）→ 桥直接落 outbox + 板。
2. **ITX 本地文件**（它自己写的）→ 要求它在回复末尾给 `FILES: <绝对路径列表>`，桥解析后 scp 回 dfy 的 `outbox/files/<task_id>/`，再随回执推板。

先只保证 (1)；(2) 列为待实现，因为客户端工作目录未确认。

## 8. 幂等与防重

- 桥内存 `busy` 集合 + 队列 `progress` 标记双保险。
- 同一任务被手动改回 queued 时，桥最多再跑一次；连续 2 次同 task 失败 → blocked。
- 推板文件名带 task_id + 时间戳，不覆盖已有文件。

## 9. 验收（可复算）

| 编号 | 场景 | 通过标准 |
|---|---|---|
| A1 | 派 3 条短任务 | 3 个独立会话、3 条回复互不混、3 个 outbox 文件、板上 3 个文件 |
| A2 | 派 1 条长任务（>2 分钟） | 不早标 done；结束时 result 含完整正文 |
| A3 | 在别的 dsh 会话里 `scnet-dispatch.sh` | 队列出现任务，桥自动接，产出回板 |
| A4 | 桥重启后 | 孤儿 doing 回收，不重复执行已 done 的任务 |
| A5 | 客户端没开 / 9223 不通 | 任务标 blocked + 板上有“端口不可达”消息，不吞任务 |

## 10. 已知缺陷（本轮实测）

1. **同一会话污染**：Q0039/Q0040 的 prompt 被塞进同一会话，串成一坨。
2. **完成判定误判**：Q0038 在“正在思考”时被判完成，结果不完整。
3. **ask 等待太短**：200s 把长生成当“无反应”。
4. **重复 claim**：手动改 queued 后旧桥立刻又抢。
5. **客户端文件够不到**：桥只拿到聊天文本，ITX 写的脚本拿不回来。

## 11. 回滚

- 桥停：`systemctl stop scnet-client-bridge`
- 恢复旧行为（不新建会话）：`SCNET_NEW_TASK=0` env
- 任务板不动；队列任务可 `update(cancelled)`。

## 13. 并发结论（2026-11-11 02:10 实测）

**能并发。** 实验：A 会话发长任务（300字）→ 1 秒后新建 B 发短任务 → B 回完后切回 A，A 的 297 字三段短文已完整生成，`停止生成` 按钮已消失。

结论：
- 切会话**不会中断**原会话的后台生成。
- 所以桥可以做「批量发射 + 顺序收集」：一次开 N 个会话各发一条，再逐个轮询完成状态。
- 会话定位靠 prompt 里埋 `[TASK:<id>]` 标记 + 左侧会话列表匹配，不靠会话标题（标题会被客户端自动改写）。
