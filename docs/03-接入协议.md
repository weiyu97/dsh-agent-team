# 03 · 接入协议与回报模板

> 这份给「对方 agent」看，也给你看——它定义了对方该怎么回报、端点格式有什么约束。

## 一、对端要提供什么

一个可接入的桌面 agent，最少提供两样：

1. 一个 **MCP streamable-http 端点**，形如 `http://<内网IP>:<端口>/mcp`；或
2. 一个可被你手动核对的接入信息（人工方式）。

## 二、端点格式约束（服务端强校）

- 只允许 `http` / `https`。
- host 只允许内网私有 IP：`10.x` / `172.16–31.x` / `192.168.x`。
- **不允许**：loopback（`127.0.0.1`）、link-local（`169.254.x`）、公网 IP、域名。
- 端口 1–65535。
- MCP 端点 URL 以 `/mcp` 结尾。

> 为什么禁 loopback：插件在 dsh 主机上探活，对端应是一个可从该主机访问的局域网地址，而不是对端自己机器上的回环。

## 三、对端应实现的 MCP 工具（探活需要）

至少实现一个 `report`：

```json
// tools/call: report -> { "open": [ { "id": "...", "title": "...", "status": "queued|doing", "queued_at": "...", "started_at": "..." } ], "counts": { ... } }
```

探活逻辑：
- 打 `report()`，HTTP 200 且 body 能解析出 `open[]` → 可达。
- `open[]` 里有 `status=doing` 且 `started_at` 距今超过 10 分钟 → 假在线。
- 解析不出 `open[]`（哪怕 200）→ 按不可达/假在线处理，不当成「可达」。

**重点**：TCP 通、`initialize` 通，都只证明端点活着，不证明它有在干活。要让它报「可达」，`report` 必须真实反映队列，且 `doing.started_at` 真实推进。

## 四、回报模板

把下面这段发给对端，让它按格式回一段，你整段粘进设置页即可自动填表：

```
【回报格式】请严格按下面模板回我，一行一个键，别加代码块、别改键名：
AGENT_ID: <唯一 id，字母开头，字母数字下划线连字符，≤32>
DISPLAY_NAME: <界面显示名，中文也行>
ENDPOINT: <完整 MCP URL，形如 http://内网IP:端口/mcp>
ROLE: <dispatcher / adjudicator / reviewer / executor / runner 五选一>
PAIRING_CODE: <把我发给你的配对码原样抄这里>

必填 AGENT_ID、ENDPOINT；DISPLAY_NAME / ROLE 可省。ENDPOINT 只收内网私有 IP、/mcp 结尾、端口 1-65535；
别写域名、公网 IP、127.0.0.1、169.254.x。回整段给我，我这边粘进设置页就能自动填表。
```

**安全红线**（也在提示词里）：Bearer token / 密码 / API key 一律不要写进回报、不要贴消息板或聊天；凭据只放对端自己机器的文件，回一句「token 已落本机」即可。

## 五、岗位语义

| id | 中文 | 大致职责 |
|---|---|---|
| dispatcher | 协调 | 拆解 / 派活 / 催办 / 收口（不直接对外派执行类） |
| adjudicator | 判官 | 只出参谋意见、无否决权 |
| reviewer | 复核 | 对抗性复核、前提校验 |
| executor | 执行 | 承接执行类任务，回执要验 |
| runner | 跑腿 | 跑探活 / 入队类，dispatch 需挂 verify 句柄 |

岗位只是登记用的标签，插件本身不据此自动派活。
