# 04 · 安全模型与已知局限

> 这份讲威胁模型、能力边界、以及——**没验过的、没做到的，如实列在这里，不粉饰。**

## 一、信任边界

- 插件跑在 dsh 主机上，HTTP 路由（`/agent-access/*`）**只接受本机回环（loopback）**。跨机访问请置于可信反向代理后，并自行加固。
- 所有对输入的校验都在 Host 侧做；客户端（设置页）的校验只是体验，不作数。
- `registry.json` / `pairs.json` / `tokens.json` / `mailbox.json` 都是**可重建的本地状态**，不是不可替代的真源。删掉可重置。

## 二、几条不变式（改代码别退化）

1. **信任字段服务端独占**：`verified / verified_at / fingerprint / pairing_id` 由服务端写；客户端 POST 带任一字段直接 400。改了 `agent_id` / `transport` / `endpoint` 任一项，自动撤销 `verified`。
2. **配对码真比对**：服务端存 `sha256(code)` + 过期时间 + 一次性标记；客户端只拿到展示串。错码 / 过期 / 重放一律拒。
3. **凭据不回显**：Bearer token 存 `tokens.json`（600），`GET /agent-access/tokens` 只回 `{has:{...}}`，不回值。SSH 密码只从本机 `mailbox.env` 读，不进界面、不进日志。
4. **私有网段白名单**：端点 host 只允许 RFC1918 私有 IP，禁 loopback / link-local / 公网 / 域名，fail-closed。
5. **CSRF 防护**：POST 强制 `application/json` + 自定义头 `X-Agent-Access: 1`；跨站 simple request 发不出 JSON、跨站带自定义头会触发 preflight 而本路由不回 CORS 头。

## 三、已知局限（如实，不假装）

- **配对码是人事确认，不是双向身份凭据。** 它证明「你确认过对方回报了这个码」，不证明对端身份、不防中间人。要变技术凭据得引入签名或双向 TLS，本插件没做。
- **跨站浏览器实测未做。** CSRF 的防护建立在「强制 JSON + 自定义头触发 preflight」的机制推断上，未做完整的跨站攻击实测。别把它当「已彻底防住」。
- **探活是乐观下限，不是保证。** HTTP 200 且能解析出 `open[]` 才判可达；但「端点活着」不等于「在里面真干活」，所以才用 `doing.started_at` 卡龄兜底（>10 分钟判假在线）。对端如果不老实填 `started_at`，这套判据会失真。
- **共享信箱的远程探测需要 `sshpass` + 密码**，走的是密码路径；当前版本不走纯密钥路径。SSH 用 `StrictHostKeyChecking=no`（首次连接不校验主机指纹），在同网段可信环境下可接受，跨不可信网络请自行配 `known_hosts`。
- **HTTP 路由只收 loopback**：如果你从另一台机器直接访问 dsh（非反代），会 403。这是有意的安全默认，不是 bug。
- **本版未做**：多语言文档（仅中文）、CONTRIBUTING 流程、自动化 CI、npm 发布。插件以 dsh bundle 形式分发。

## 四、升级 / 回滚

- 改代码前先备份，改完验证（`node --check`、装进测试 profile 跑一遍）。
- 出问题回滚到备份文件，把插件 `enabled=false` 再 `true` 触发重载。
- 数据（`registry.json` 等）与代码分离，回滚代码不影响已登记数据。

## 五、报告安全问题

发现安全相关问题，请开 issue 描述复现方式，别贴真实凭据。
