# 06 · 共享信箱驱动唤醒（联动手册，外部方法记录）

> 边界先说清：**本插件只做「接入登记 + 诚实探活 + 共享信箱读写」，不派活、不自动回信、不替对端干活。**
> 这一节和 docs/05 一样，是作者在自己环境里把「信箱里来的活真正叫醒对端」跑起来的方法记录，**不随插件分发**，路径与 IP 都请按自己的环境替换。

## 一、为什么还要一节「唤醒」

共享信箱只解决**送达**：文件躺在共享板上，对端不动，活还是没人干。
实测反复印证同一件事：**投递成功 / 入队成功 / 状态置 done，都不等于有人执行。**

三个真实面孔（2026-11-12 实测，都是同一台对端）：

| 现象 | 真相 |
|---|---|
| MCP `dispatch` 返回 `{ok:true, id:..., status:"queued"}` | 只是进队列，worker 没领也一样是 queued |
| 队列把它置成 `doing`→`done` | 对端常驻 worker 只做**落地与核对**，`result` 里自己写着「语义执行待会话接手」 |
| `fetch_result(id)` 取回的产出 1753/1556 字节 | 内容就是**你投进去的任务原文**，零证据、nonce 不出现 |

所以「唤醒」是独立的一环：把**信箱里的新消息**变成**对端真的动起来**。

## 二、联动链路（实测在跑的形状）

```
共享板 <BASE>/消息/  （投件方写这里）
  │  ① dsh 侧 watcher（systemd，30s 一轮）：扫 消息/ 与 回执/，把非自己发的文件拉到本机 inbox/
  ▼
本机 inbox/  →  check-inbox.sh 读取归档
  │  ② 唤醒脚本 wake-doubao.sh：只挑 to_<agent> 的**新**消息
  ▼
对端（Chromium 内核客户端，CTRL 走 CDP）
  │  ③ ssh 到对端跑 wrapper：读 prompt 文件 → CDP 新建对话 → Input.insertText → Enter → 抓回复
  ▼
对端 outbox → ④ relay（15s）搬上共享板 产出/ 回执/ → 回到本机 inbox
```

四段各司其职：**① 收 ② 叫 ③ 干 ④ 回**。缺任何一段，链路就是「发出去没回音」或「有回音没人干」。

## 三、脚本要点（踩过才知道）

`wake-doubao.sh`（作者环境在 `~/.dsh/bin/`）的关键设计，逐条都有理由：

1. **只处理 `to_<agent>` 的新消息**：靠本地 `seen.txt` 记账，处理过的不再叫第二遍。
2. **`--seed` 首次只登记不唤醒**：第一次上线时共享板里往往积压几十条历史消息，直接跑会把它们全喂给对端（实测 79 条），既慢又乱。
3. **每轮最多唤醒 1 条**：一次唤醒要等对端模型生成 30–50s，一轮跑多条必超时；剩下的下一轮继续。
4. **prompt 走文件，不进命令行**：中文长文本经过 `bash → ssh → cmd → node` 四层引号必炸。做法是 scp 一个 `.txt` 到对端，再让一个 wrapper（`wake_doubao_file.mjs`）从文件读。
5. **密码用 `sshpass -f <文件>`，不用 `-p <明文>`**：`-p` 的密码会出现在进程列表里。
6. **Windows 路径用正斜杠**：`scp local.txt user@host:D:/path/name.txt` 能过，反斜杠在 scp 里常被吃掉。

## 四、验收纪律（照这个收，别信自报）

对端说 done，**先取原始产出再判断**：

- 产出里要出现本次任务的 **nonce**（投件时写进正文，例如 `DYOFFICIAL-1112`）——不出现就是旧稿或落地件。
- 产出**字节数与任务正文高度接近** → 判定为「落地冒充执行」，直接打回。
- 产出里 `result` 字段出现「语义执行待会话接手」「只做落地与核对」这类自述 → 同上，打回。
- 涉及文件的（帧、截图、报告）：看 **mtime 是否晚于派发时刻**，不看它自述的时间。
- 要一条**负对照**：停掉执行端再发同样任务 → 应无产出。

打回信里要写清「不合格的具体数字」和「下次按什么标准收」，否则对端会继续用同一招交差。

## 五、已知坑（2026-11-12 实测，别重复踩）

1. **对端 AI 客户端的输入层会随版本变**：本次实测 `新建对话` 能点到（`new-chat: clicked`），但抓回复一直 `ERR EMPTY_REPLY`。说明「点得到输入框」不等于「抓得到回复」——抓回复的定位方式（按 prompt 文本切片）是最脆的一环，客户端一改版就失效。修的时候先单独验证「输入→发送→回复出现」三段，别整条链路一起猜。
2. **主机不可达 ≠ 服务没起**：SCNet 那台整机 `ping` 100% 丢包、22 与 MCP 端口全 `No route to host`——这是**机器不在线**，不是服务挂了。先 ping 再谈服务，别对着一个关机的机器改配置。
3. **别动对端的计划任务来"顺手修"**：本次为了拉起某个 MCP 端口，启用了对端一个计划任务、还新建过一条；端口依旧没监听，改动属于多余动作，已全部回滚。**对端机器只做必要操作，改了就记回滚方式。**
4. **`online:true` / TCP 通 / MCP `initialize` 200 都只证明端点活着**，不证明它这一轮真干了活。判定「真在线」要落到「doing 真的推进了 / 产出真的落盘了」。
5. **共享板里自己发的文件会被 watcher 跳过**（文件名含 `__linux-agent__`），这是有意的：避免自己的投件被自己拉回来当新消息。

## 六、回滚

- 停联动：删 `~/.dsh/bin/wake-doubao.sh`（或不再跑）即可，注意它只写自己的 `~/.dsh/agent-wake-doubao/` 目录，不碰别的链路。
- 停收件：`systemctl stop dsh-ftp-watch`（重启用 `start`）。
- 停 relay：`systemctl stop doubao-board-relay`（对端 outbox 不再搬上共享板，其余不变）。
